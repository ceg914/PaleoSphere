# 성능: 측정치와 목표

**목표**는 기획서의 요구 수치이고 **측정치**는 실제로 잰 값입니다. 둘을 섞어 쓰지 않습니다.

## 목표 (기획서 6장, 기준 PC: i7-8700K, GTX 1070 Ti 8GB, RAM 32GB)

| 지표 | 1차 목표 | 정식 1.0 목표 |
|---|---|---|
| 해상도 | 1920×1080 | 1920×1080 |
| 프레임률 | 30 FPS 이상 | 중간 품질 60 FPS 지향 |
| 활성 개체 | 100 | 500, 부하 시험 1000 |
| 세계 크기 | 512×512 m | 2×2 km 선택형 |
| 장시간 실행 | 1시간 | 8시간 이상 |

## 측정 환경

기준 PC가 아닙니다. Intel Xeon 2.10GHz 4코어, RAM 15 GB, **GPU 없음**, Ubuntu 24.04, .NET 8.0.34. 2026-11-17 측정.

## 측정치: 틱 처리 시간 (화면 없음, Release 빌드)

`tools/SimRunner`로 `lush_lowland` 시나리오를 돌렸습니다.

| 조건 | 틱당 평균 | 최대 | 의사결정·생리 | 이동 | 식생(갱신 틱만) |
|---|---|---|---|---|---|
| 512 m, 100개체, 2일 | 30.7 µs | 9.0 ms | 0.003 ms | 0.007 ms | 0.31 ms |
| 512 m, 500개체, 2일 | 131.2 µs | 9.4 ms | 0.028 ms | 0.055 ms | 0.32 ms |
| 512 m, 1000개체, 2일 | 320.1 µs | 9.9 ms | 0.063 ms | 0.183 ms | 0.31 ms |
| 2 km(1000×1000셀), 1000개체, 0.5일 | 335.4 µs | 18.1 ms | 0.025 ms | 0.097 ms | 5.10 ms |

읽는 법:

- 10배속은 초당 100틱입니다. 1000개체에서도 틱 계산은 초당 약 32 ms라, 이 CPU에서는 시뮬레이션이 10배속의 병목이 아닙니다.
- 2 km 세계에서는 식생 갱신(50틱마다 100만 셀)이 한 번에 5.1 ms 걸립니다. 60 FPS의 프레임 예산(16.7 ms)을 잡아먹는 크기라, 큰 세계를 지원하려면 격자를 여러 틱에 나눠 갱신해야 합니다.
- 최대값 9~18 ms의 원인은 따로 분석하지 않았습니다(시작 직후의 JIT 컴파일, 식생 갱신 틱, GC가 후보입니다).
- 2 km 세계 생성에는 1.7초가 걸렸습니다(512 m는 0.3초).
- 이동이 개체 수에 비례 이상으로 늘어납니다(100 → 1000개체에서 26배). 512 m에 1000마리면 서로 겹쳐 분리 계산이 많아지기 때문입니다.

엔진 안(디버그 빌드, 30개체)에서는 틱당 51~56 µs였습니다.

위 표는 수학 함수를 직접 구현한 것(`DetMath`)으로 바꾼 뒤에 다시 잰 값입니다. 바꾸기 전과 차이는 측정 오차 범위였습니다.

## 측정치: 게임 프레임의 CPU 시간 (렌더링 없음)

리깅 모델과 지피 식생을 넣은 뒤, 화면을 그리지 않는 모드(`--headless`)에서 `--benchmark`로 잰 값입니다. 뼈대 애니메이션, 식생 크기 갱신, UI 갱신, 시뮬레이션이 포함되고 GPU 작업은 빠져 있습니다. 2026-11-17, 같은 개발 환경.

| 개체 수 | 평균 프레임 | 틱 평균 |
|---|---|---|
| 30 | 6.90 ms | 0.123 ms |
| 100 | 6.91 ms | 0.208 ms |
| 500 | 8.58 ms | 0.533 ms |

30~100마리에서 프레임이 같은 것은 이 모드의 프레임 상한(약 145 FPS)에 걸렸기 때문으로 보입니다. 화면을 그리는 비용은 여전히 측정하지 못했습니다.

## 측정치: 장시간 실행 (화면 없음)

512 m, 100개체로 시작해 900만 틱(게임 내 1500일)을 98초에 실행했습니다(수학 함수 교체 전에 측정).

| 시점 | 관리 힙 | 작업 집합 | 통계 표본 수 |
|---|---|---|---|
| 250일 | 2.1 MiB | 39.7 MiB | 1501 |
| 750일 | 2.1 MiB | 40.0 MiB | 2251 |
| 1500일 | 2.1 MiB | 41.1 MiB | 2251 |

통계 표본과 행동·사건 로그는 개수 한도가 있어 메모리가 계속 늘지 않습니다.

## 측정하지 못한 것

| 항목 | 이유 | 재는 방법 |
|---|---|---|
| FPS, 프레임 시간, GPU 사용량 | 개발 환경에 GPU가 없음. 소프트웨어 Vulkan(llvmpipe)으로 1600×900에서 2~4 FPS가 나왔지만 실제 PC의 성능과 무관함 | `PaleoSphere.console.exe -- --benchmark=100 --seconds=20` (개체 수를 500, 1000으로 바꿔 반복) |
| 창을 띄운 채 1시간·8시간 | 같은 이유 | 게임을 켜 두고 `성능 분석` 탭과 작업 관리자의 메모리 확인 |
| 기준 PC에서의 틱 시간 | 기준 PC가 없음 | `dotnet run --project tools/SimRunner -c Release -- --days 2 --count 1000 --quiet` |

`--benchmark`는 한 줄로 개체 수, 평균 FPS, 프레임 시간, 틱 평균·최대, 실효 배속, 그래픽 어댑터 이름을 출력합니다. 결과를 이 문서의 표에 추가해 주세요.

## 목표 대비 현재 판단

| 목표 | 판단 |
|---|---|
| 100개체 | 틱 계산은 여유가 큼. 화면은 미측정 |
| 500~1000개체 | 틱 계산은 10배속까지 가능해 보임. 리깅 모델은 개체마다 스켈레톤과 애니메이션을 따로 계산하므로 1000마리에서는 CPU 부담이 커질 수 있음(260 m 밖은 애니메이션을 멈춤). GPU 측정 후 판단 |
| 2 km 세계 | 생성·실행은 됨. 식생 갱신 분산과 지형 메시 청크·LOD가 필요. 새 세계 창에서는 1024 m까지만 고를 수 있음 |

## 이미 적용한 기법

고정 틱, 개체 id로 엇갈린 갱신 주기, 물까지의 거리장(개체 수와 무관), 공간 해시(이웃 탐색), 프록시 풀링, 나무 MultiMesh, 거리별 세부 숨김, 프레임당 시뮬레이션 시간 한도와 실효 배속 표시.
