## 결정

### 1. 시뮬레이션 코어를 별도 어셈블리로 분리

`src/PaleoSphere.Sim.csproj`는 Godot를 참조하지 않는 순수 .NET 라이브러리입니다. 게임 프로젝트(`PaleoSphere.csproj`)가 이를 참조합니다.

- 테스트가 엔진 없이 `dotnet test`로 돕니다.
- 코어에서 Godot API를 실수로 쓰면 컴파일이 안 됩니다. 규칙이 아니라 구조로 분리를 강제합니다.
- 기획서의 폴더 구조(`src/Core`, `src/World` …)는 그대로 두고, 프로젝트 파일이 폴더를 골라 컴파일합니다.

### 2. 표현 계층은 스냅샷만 읽고, 변경은 명령으로만

UI와 렌더러는 `SimSnapshot`(복사본)과 `GetDetails()`(복사본)를 읽습니다. 세계를 바꾸려면 `ISimCommand`를 큐에 넣고, 코어가 틱 경계에서 검증한 뒤 순서대로 적용합니다. 일시정지 중의 배치도 같은 경로를 탑니다.

### 3. 고정 틱과 재현성

- 한 틱은 이동 기준 0.1초입니다. `FixedTimestepDriver`가 프레임 시간을 틱으로 바꾸고, 렌더러는 이전·현재 위치를 보간합니다.
- 난수는 직접 구현한 PCG32입니다. `System.Random`은 런타임 버전에 따라 수열이 달라질 수 있어 쓰지 않았습니다. 개체마다 `(세계 시드, 개체 id)`로 만든 독립 수열을 갖습니다.
- 개체는 항상 id 순서로 처리하고, 이동은 "모두의 희망 속도 계산 → 한꺼번에 적분" 두 단계라 처리 순서가 결과에 영향을 주지 않습니다.
- 코어는 단일 스레드입니다. 멀티스레딩은 Phase 5에서 측정 결과를 보고 결정합니다.
- **수학 함수는 직접 구현한 `DetMath`만 씁니다.** `MathF.Sin`·`Cos`·`Atan2`·`Exp`는 운영체제 수학 라이브러리를 부르는데, 이 라이브러리가 CPU에 따라 다른 구현을 골라 마지막 비트가 달라집니다. 실제로 개발 환경과 CI 러너의 기준 해시가 달랐고, 사칙연산만 쓰는 구현으로 바꾼 뒤 일치했습니다. `Sqrt`·`Floor`·`Abs`처럼 IEEE 754가 정확한 결과를 정해 둔 연산은 그대로 씁니다.
- **확인한 범위:** 개발 환경(Linux x64), GitHub Actions의 Ubuntu·Windows 러너(x64)에서 기준 해시가 같습니다. Debug와 Release도 같습니다. ARM 등 다른 CPU 구조는 확인하지 않았습니다.

### 4. 하루 길이 압축

게임 내 하루는 6000틱(1배속에서 10분)입니다. 생리·식생 속도는 "게임 내 하루/시간" 단위로 정의하고 시계가 틱으로 바꿉니다. 이동 속도는 초당 미터 그대로라, 하루에 걸을 수 있는 거리가 실제보다 훨씬 짧습니다. 관찰하기 좋은 속도를 얻으려는 게임적 단순화입니다.

### 5. 경로 탐색은 거리장 + 직선 조향 (P0)

- 물로 가는 길: 물가 셀에서 출발하는 다익스트라 거리장을 한 번 계산해 두고, 개체는 거리가 줄어드는 이웃 셀로 갑니다. 개체 수와 무관하게 비용이 일정합니다.
- 그 밖의 목표: 직선 조향. 막히면 좌우로 틀어 피하고, 계속 막히면 목표를 버립니다.
- 목표를 고를 때 직선으로 걸어갈 수 있는지 먼저 검사합니다. 이 검사가 없던 초기 구현에서는 강가의 개체가 건널 수 없는 건너편 먹이를 계속 노리다 굶어 죽었습니다.
- 계층형 A*는 Phase 5 과제입니다.

### 6. 세이브 형식: gzip으로 압축한 JSON

머리말(형식 이름, `schema_version`, `simulation_version`, 시드, 상태 해시, SHA-256 체크섬, 요약)과 `state`로 이뤄집니다. 지형·식생 배열은 float32 리틀 엔디언 바이트를 Base64로 담아 비트 단위로 복원합니다. 지형은 시드에서 다시 만들지 않고 통째로 저장합니다. 생성기를 고쳐도 옛 세이브의 지형이 바뀌지 않게 하기 위해서입니다.

### 7. UI는 코드로 구성, 글꼴은 시스템 글꼴

에디터 없이 검증 가능한 범위를 넓히려고 `.tscn`은 진입점 하나만 두고 UI를 C#으로 만들었습니다. 한글 글꼴 파일을 싣지 않고 `SystemFont`로 운영체제 글꼴을 씁니다(라이선스 확인이 필요한 파일을 배포하지 않기 위함).

### 8. 렌더러

Forward+(Vulkan)입니다. 개체는 종 데이터의 `model` 항목에 적힌 리깅 모델을 쓰고(뼈 39개, AnimationPlayer), 없으면 코드로 만든 메시로 대체합니다. 260 m보다 멀면 애니메이션 계산을 멈추고(자세는 유지), 90 m보다 멀면 위치 표식을 띄웁니다. 나무는 MultiMesh입니다. 개체 수가 수백을 넘을 때의 드로 콜 비용은 GPU가 있는 PC에서 재 봐야 하며, 필요하면 개체도 MultiMesh로 바꿉니다.

### 9. 모델 연결 방식

- 모델 정보(경로, 출처, 라이선스, 길이, 보폭, 애니메이션 이름)는 종 JSON의 `model` 항목에 둡니다. 경로는 `res://assets/` 아래로 제한합니다.
- 크기: 모델의 머리끝–꼬리끝 길이(뼈 위치로 잼)를 종의 몸길이에 맞춥니다.
- 걷기·달리기: 애니메이션에서 땅에 닿은 발이 뒤로 가는 속도를 재 두고(`tools/godot/measure_gait.gd`), 재생 속도 = 실제 이동 속도 ÷ 그 속도로 정합니다. 발이 미끄러져 보이지 않습니다.
- 원본 팩에 없는 자세(먹기, 마시기, 쉬기)는 `SkeletonModifier3D`로 애니메이션 위에 뼈 회전을 덧입혀 만듭니다. 회전축을 모델 좌표로 정하고 뼈마다 지역 좌표로 바꾸므로, 뼈 이름이 같은 다른 공룡 모델에도 그대로 씁니다.

### 10. 식물 표시

- 지피 식생은 64 m 타일마다 MultiMesh 하나씩, 190 m 밖은 그리지 않습니다. 프레임마다 타일 두 개씩 셀 식생량에 맞춰 크기를 갱신합니다(`RenderingServer.MultimeshSetBuffer`로 한 번에 씀).
- 식물 형태는 헬크리크층 식생 구성(속씨식물 활엽수, 침엽수, 양치류, 소철·베넷티테스류, 속새)을 대략 따른 양식화 표현입니다. 풀밭은 신생대에 퍼졌으므로 만들지 않았습니다.

### 11. 물리 엔진을 쓰지 않음

마우스 선택은 높이맵 광선 추적과 광선-구 교차로 직접 계산합니다. 충돌체·물리 스텝이 없습니다.
